# Feature Specification: AstroPaper 上游版本差异审计（6.1.0 → 最新）

**Feature Branch**: `004-astropaper-upgrade-audit`

**Created**: 2026-11-21

**Status**: Draft

**Input**: User description: "看一下 astro paper 从 6.1.0 到 最新版更新了哪些功能，和我们做一下对比看看有没有我们这边需要更新的"

## Clarifications

### Session 2026-11-21

- Q: 交付物是什么形态——直接改代码升级，还是先出对比评估？ → A: 交付物是**对比审计报告**：
  梳理上游 satnaing/astro-paper 从 6.1.0 到当前最新版的全部变更，逐项对照本站现状给出
  "需采用 / 已自研等价 / 不适用 / 需权衡"四类判定与优先级，采用决策权归维护者；实际升级
  属后续独立特性，由维护者评审报告后单独发起。
- Q: 对比的"我们这边"以什么为基准？ → A: 以仓库当前实际状态为基准（含本会话刚完成的
  astro 7.4.13 升级与 Sätteri 管线迁移），而非某个历史时点；上游变更逐项对照本站的
  自研清单（双语路由、书籍章节、callouts、mermaid、OG、Sätteri 管线等）判定是否已被
  等价实现覆盖。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 看清上游到底变了什么 (Priority: P1)

维护者打开报告，能看到上游 6.1.0 → 最新版的完整变更清单：每个版本发了什么、哪些是
功能特性、哪些是修复、哪些是破坏性变更，且每项附可复核的来源（release notes / commit）。

**Why this priority**: 没有可信的变更清单，后续一切对比与决策都无从谈起。

**Independent Test**: 抽查报告中任意 5 条上游变更，均能在上游仓库 release/commit 中得到
验证，无凭空捏造项。

**Acceptance Scenarios**:

1. **Given** 上游发布 6.1.0 之后的若干版本，**When** 维护者阅读报告第 2 章，**Then**
   每个上游版本单独成行，含版本号、发布日期、变更摘要与来源链接。
2. **Given** 某上游版本含破坏性变更，**When** 维护者查看该项，**Then** 破坏性变更
   显式标注，并说明对本站的可能影响。

---

### User Story 2 - 知道每一项上游变更对本站的适用性 (Priority: P1)

维护者能看到变更清单与本站现状的逐项对照：每项上游变更为"本站已自研等价 / 需要采用 /
不适用 / 需权衡"之一，判定带依据（指向本站对应实现文件或上游 commit），需要采用的项
给出优先级与预估工作量档位（S/M/L）。

**Why this priority**: 这是报告的核心价值——把"上游变了什么"转化为"我们该做什么"的
可决策清单。

**Independent Test**: 抽取任一"需要采用"判定，核对依据同时覆盖上游变更内容与本站现状
两处证据；抽取任一"已自研等价"判定，能在本站代码中找到对应实现文件。

**Acceptance Scenarios**:

1. **Given** 上游新增了某功能，**When** 查看其判定，**Then** 明确标注本站是已有等价
   实现（附文件路径）、需要采用、还是不适用（附原因，如与双语架构冲突）。
2. **Given** 某项判定为"需要采用"，**When** 维护者查看，**Then** 该项有优先级
   （P1/P2/P3）与工作量档位（S/M/L），并能追溯上游来源。
3. **Given** 本站已偏离上游的架构决策（如 Sätteri 管线、书籍章节、i18n），**When**
   上游在相同区域有变更，**Then** 报告显式标注冲突风险，而不是笼统写"可升级"。

---

### User Story 3 - 拿到可执行的采用路线 (Priority: P2)

维护者看完报告能直接决策：哪些项现在就值得做、哪些等上游稳定、哪些永远不采用，并且
对"需要采用"的高优先级项有一句话级别的实施建议（动哪些区域、有什么风险）。

**Why this priority**: 报告的终点是决策，不是信息陈列。

**Independent Test**: 维护者仅阅读报告结论章，能在 10 分钟内圈定"立即采用 / 暂缓 /
不采用"三组清单。

**Acceptance Scenarios**:

1. **Given** 报告完成，**When** 维护者阅读结论章，**Then** 三组清单（建议立即采用 /
   暂缓观察 / 不采用）齐备，每组各项可追溯到前文判定。
2. **Given** 某高优先级采用项，**When** 阅读其实施建议，**Then** 建议含涉及区域与
   风险提示，且不与本站宪法原则（静态优先、i18n 等价、质量门禁）冲突。

---

### Edge Cases

- 上游某变更在本站因架构偏离已无法直接对比（如上游重构了同一文件而本站已重写）：判定
  MUST 标注"路径分叉"，说明双方现状而非强行归类。
- 上游版本号跳跃或不规范（如跳过某 minor）：报告 MUST 以实际 release 记录为准，不做
  版本号推演。
- 上游某依赖本站已升级到更高版本（如 astro 7.4.13 高于上游锁定版本）：判定 MUST 注明
  "本站领先"，并评估上游变更是否仍适用。
- 上游 release notes 缺失或过于简略：MUST 交叉核对 commit 历史，MUST NOT 凭版本号猜测
  变更内容。
- 本站自研功能与上游新功能表面相似但语义不同（如 TOC）：判定 MUST 说明语义差异，
  MUST NOT 仅凭名称相似判为等价。
- 调研存在时间截面：报告 MUST 标注数据截止日期，此后上游新发布不在此范围。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 报告 MUST 以 satnaing/astro-paper 官方仓库为准，梳理 6.1.0 之后至最新
  稳定版的全部版本发布，MUST 覆盖所有中间版本，MUST NOT 遗漏任何 minor/major 版本。
- **FR-002**: 每个上游版本 MUST 记录：版本号、发布日期、变更分类（新功能 / 修复 /
  重构 / 依赖升级 / 破坏性变更）、摘要、可复核来源链接。
- **FR-003**: 全部上游变更 MUST 与本站现状逐项对照，判定 MUST 取以下四类之一：
  `adopt`（需要采用）/ `already_have`（本站已自研等价）/ `not_applicable`（不适用）/
  `tradeoff`（需权衡），MUST NOT 使用"视情况而定"等不可决策的类别。
- **FR-004**: 每项判定 MUST 附双重证据：上游侧（release/commit 链接）+ 本站侧
  （现状描述或实现文件路径）；证据不足的项 MUST 标注"证据不足"而非猜测。
- **FR-005**: `adopt` 项 MUST 给出优先级（P1/P2/P3）与工作量档位（S/M/L），
  P1 项 MUST 附一句话实施建议（涉及区域 + 风险）。
- **FR-006**: 本站的架构偏离区（i18n 双语路由、书籍章节体系、callouts/mermaid/
  OG 生成、Sätteni 管线、暗色模式实现等自研区）MUST 建立对照清单，上游触及这些区域
  的变更 MUST 标注冲突风险。
- **FR-007**: 报告 MUST 标注数据截止日期；上游在此日期后的发布 MUST 列入"复核提示"
  而非纳入正文。
- **FR-008**: 报告 MUST 以中文撰写，术语首次出现附英文原名；结论章 MUST 给出
  三组决策清单（建议立即采用 / 暂缓观察 / 不采用）。
- **FR-009**: 本次交付物 MUST 仅限审计报告本身（位于本特性目录下），MUST NOT 修改
  站点代码、依赖或配置；实际采用工作属后续特性，由维护者评审后发起。
- **FR-010**: 报告中引用的每一条上游事实 MUST 可复核（release 页、commit 链接或
  官方文档），MUST NOT 出现无来源的版本号、功能名或行为断言。

### Key Entities *(include if data involved)*

- **上游版本记录**：上游的一个 release，含版本号、日期、分类、变更摘要、来源链接。
- **变更对照项**：一条上游变更 × 本站现状的判定，含四类判定、双重证据、优先级、
  工作量档位、冲突风险标注。
- **本站自研区清单**：本站偏离上游的架构区域及其实现位置，作为判定 `already_have`
  与冲突风险的参照系。
- **决策清单**：结论章的三组列表（立即采用 / 暂缓观察 / 不采用），各项追溯对照项。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上游 6.1.0 → 最新版的全部版本在报告中零遗漏（以官方 releases 页为
  核对基准，抽查 5 条可验证）。
- **SC-002**: 全部上游变更 100% 获得四类判定之一，每项判定带上游+本站双重证据，
  抽查 10 条证据缺失数为 0。
- **SC-003**: 本站自研区清单完整覆盖已知偏离区（≥8 项），触及自研区的上游变更
  100% 标注冲突风险。
- **SC-004**: 维护者仅阅读结论章即可在 10 分钟内完成"立即采用 / 暂缓 / 不采用"
  分组决策，无需回查上游仓库。
- **SC-005**: 报告数据截止日期明确标注，来源链接抽查 5 条全部可访问。
- **SC-006**: 站点代码、依赖、配置零改动（`git status` 变更仅限 specs/ 与
  .specify/）。

## Assumptions

- "6.1.0" 指本站 package.json 中的版本基线（对应上游 AstroPaper v6.1.0 分叉点）；
  上游侧以 satnaing/astro-paper 官方 releases 为唯一事实来源。
- 上游最新版的调研以数据截止日（见报告）为准，不做滚动跟踪。
- 判定"需要采用"不等于立即实施——本特性只产出决策依据，实施属后续特性。
- 本站当前状态取本会话完成后的快照：astro 7.4.13、Node 24.21.0、Sätteri 管线、
  双语（zh 默认 + en）、书籍章节、callouts/mermaid/OG/搜索等自研能力均已就位。
- 上游变更若与本站宪法原则冲突（如引入服务端能力），一律判 `not_applicable` 并注明
  宪法依据。
