## Clarifications

### Session 2026-11-17

- Q: 这份调研最终要推荐"框架"，还是要推荐"具体主题/模板"，还是两者分层都推荐？ → A: 框架锁定 Astro，不再做框架选型；主题可从 Hugo、Next.js 等其他生态取材，最终适配移植到 Astro。
- Q: "类似本风格"应该理解成保持当前的克制极简排版，还是允许更强烈的视觉风格？ → A: 不做风格限制，极简、Material 3、动漫风、玻璃拟态、终端风等全部纳入候选并分档呈现，最终由维护者评审拍板。
- Q: 候选池应该收多少主题，才既符合"不要漏掉"又不至于让报告失控？ → A: 不设数量上限，检索命中的主题全部进入深度核验，不做截断抽样。
- Q: 每个候选的首屏截图，你希望我实际抓取生成，还是只提供演示链接供你自己点开看？ → A: 只提供可访问的演示链接，不生成落盘截图或缩略图拼版，报告保持最轻。
- Q: 这次的交付物应该停在调研报告，还是要同时产出可运行的代码改动？ → A: 只交付调研报告，不改动任何应用代码、依赖或构建配置。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 选出值得移植的高颜值主题 (Priority: P1)

维护者已经决定继续使用 Astro，但认为当前 AstroPaper 主题在视觉上不够前沿。他打开一份候选池，在每个主题上看到仓库地址、星标数、最近更新时间、许可证，以及可直接访问的在线演示，并能按自己的标准圈定想移植的目标。

**Why this priority**: 这是本次调研的核心产出。没有可信、可比较、可访问的视觉候选，后续适配工作无从开始。

**Independent Test**: 把候选池单独交给一位维护者，若其能在 20 分钟内从中圈定目标主题且无需额外搜索，即视为通过。

**Acceptance Scenarios**:

1. **Given** 候选池已完成，**When** 维护者从上往下浏览，**Then** 每个候选都带有可访问的演示站点链接，不存在只有文字描述而无实物的条目。
2. **Given** 候选跨越不同视觉风格，**When** 维护者浏览，**Then** 候选按风格分档归组，且没有任何风格因"不符合本风格"被预先剔除。
3. **Given** 候选来自多个生态，**When** 维护者查看某个 Hugo 或 Next.js 主题，**Then** 清单明确标注其原始生态，并说明移植到 Astro 需要重建的部分。
4. **Given** 维护者担心踩到已废弃项目，**When** 查看任一候选，**Then** 能看到最近提交时间、最近发版时间与维护活跃度证据。
5. **Given** 两个候选视觉接近，**When** 维护者比较，**Then** 能通过统一的评估维度与演示链接自行判断差异，而非只靠"感觉更好看"。

---

### User Story 2 - 确认主题能承载本站既有能力 (Priority: P1)

维护者担心某个主题看起来惊艳，但移植后中文排版崩坏、双语路由失效、书籍章节导航无法实现、搜索和图片灯箱要推倒重来。他需要看到每个候选主题在保留本站能力上的代价判定。

**Why this priority**: 视觉吸引力如果不附带能力代价，推荐就会变成陷阱。缺少这层，选出的主题可能在实施阶段被放弃。

**Independent Test**: 抽取任一候选主题，核对其在本站能力清单的每一项上都有"可直接沿用 / 需改造 / 需重建 / 与主题冲突"的判定与依据。

**Acceptance Scenarios**:

1. **Given** 候选主题以英文单语为主，**When** 查看中文与双语支持判定，**Then** 给出中文字体回退、字数统计、标点间距、缺失译文回退等具体影响，而非只写"支持 i18n"。
2. **Given** 本站有目录驱动的书籍章节体系，**When** 查看该主题的侧边栏与章节导航判定，**Then** 说明是可直接映射、需要改造还是需要重建。
3. **Given** 候选主题自带搜索或图片灯箱，**When** 查看判定，**Then** 说明其方案能否在纯静态托管下工作，以及是否能替换现有方案。
4. **Given** 主题依赖本站不需要的重型交互，**When** 查看代价，**Then** 明确列出可剥离的部分与被剥离后是否仍保留原有视觉特征。

---

### User Story 3 - 估算移植代价并排出实施顺序 (Priority: P2)

选定主题后，维护者需要知道把它搬到 Astro 上要分几步、每步产出什么、哪一步可以回退，以及在移植期间原站点是否始终可发布。

**Why this priority**: 移植是可失败的工程动作。没有阶段划分与回退点，风险不可控。

**Independent Test**: 仅阅读移植章节，即可判断该主题能否在一个可接受的工作量内落地，并知道第一阶段的产出是什么。

**Acceptance Scenarios**:

1. **Given** 报告推荐某个主题，**When** 阅读移植章节，**Then** 看到按视觉外壳、布局与组件、内容模型对接、搜索与 SEO、部署切换划分的阶段与每阶段产出。
2. **Given** 移植中途失败，**When** 查看回退方案，**Then** 明确指出现有站点在哪个节点之前仍可正常发布。
3. **Given** 主题来自非 Astro 生态，**When** 查看工作量估算，**Then** 估算区分"可直接迁移的静态资源"与"必须重写的模板逻辑"。
4. **Given** 维护者只想小步改进，**When** 阅读同一章节，**Then** 能看到只移植视觉外壳、不动内容模型的最小可行路径。

---

### Edge Cases

- GitHub 星标数高但最近两年无提交：候选 MUST 记录最近提交时间，且 MUST NOT 仅凭星标数进入推荐位。
- 主题演示站点已下线或需付费购买：候选 MUST 标注演示可达性与许可证类型，无法验证视觉效果的主题 MUST 被降级处理。
- 主题的"好看"依赖大量客户端动画或 WebGL：候选 MUST 标注运行时脚本负担与在低端设备或减少动效偏好下的降级表现。
- 主题仅提供英文排版优化：候选 MUST 说明中文标点、行高、字重与字体回退的改造量。
- 主题为付费或非开源许可：候选 MUST 标注许可限制，并说明是否可用于本站。
- 主题所属框架与 Astro 的模板语法差异极大：候选 MUST 说明是"取样式与结构重写"还是"可直接复用组件"。
- 调研期间新主题突然走红：报告以调研截止日期为界，截止后变化 MUST 在时效性说明中提示复核。
- 候选清单里出现与当前 AstroPaper 高度相似的主题：报告 MUST 明确指出"相似度"并说明移植收益是否足以抵消成本。
- 用户已删除 `AGENTS.md` 等本地指导文件：结论 MUST NOT 依赖这些已不存在的文件，MUST 以仓库实际存在的配置与内容为准。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 调研 MUST 锁定 Astro 作为唯一目标框架，MUST NOT 再产出"是否迁移到其他框架"的选型结论。
- **FR-002**: 主题取材范围 MUST 跨生态，MUST 至少覆盖 Astro、Hugo、Next.js 三类的博客主题，并 MAY 纳入 Eleventy、SvelteKit、Zola、Jekyll 等生态。
- **FR-003**: 检索 MUST 使用 GitHub 高级搜索的组合条件，且 MUST 记录实际使用的查询式（含 `topic:`、`stars:`、`pushed:`、`created:`、`license:` 等限定符），使检索过程可复现。
- **FR-004**: 检索 MUST 同时覆盖"高星标长期流行"与"近期新增高增长"两类，MUST NOT 只按星标总数排序而漏掉新近走红的项目。
- **FR-005**: 候选池 MUST NOT 设数量上限或抽样截断；所有满足纳入条件的主题 MUST 全部进入深度核验。
- **FR-006**: 由于候选池不设上限，"全部纳入"的执行边界 MUST 由显式纳入条件定义，至少包含：仓库自述或 topic 标注为博客/写作/内容站点用途、最近 12 个月内有提交、具备可访问的演示链接或可核验的视觉说明。检索命中但不满足条件者 MUST 记录为"已检索未纳入"并附原因，使检索覆盖率可核算。
- **FR-007**: 候选主题 MUST 满足最低维护门槛：最近一次提交在调研截止日前 12 个月内，且非归档状态；不满足者 MUST 记录排除原因。
- **FR-008**: 每个候选 MUST 提供：仓库地址、星标数、创建时间、最近提交时间、最近发版时间、许可证、原始生态与技术栈、在线演示地址。
- **FR-009**: 视觉证据 MUST 以可访问的演示站点链接形式提供，报告 MUST NOT 生成或落盘截图、缩略图或视觉拼版；演示不可达的候选 MUST 明确标注"演示不可达"并说明后续复核方式，MUST NOT 静默省略。
- **FR-010**: 视觉评估 MUST 使用统一维度，MUST 至少包含：排版与字体层次、配色与对比度、布局密度与留白、动效与交互、响应式表现、暗色模式质量、首屏冲击力。
- **FR-011**: 视觉维度 MUST 由维护者可复核的判断口径定义（例如"是否具备清晰的字号阶梯与行宽控制"），MUST NOT 只写"好看""现代感"这类无法验证的形容；维度判定 MUST 标注依据来自仓库文档、演示可观察特征或主题源码，MUST NOT 声称视觉结论来自未实际生成的截图。
- **FR-012**: 每个候选 MUST 针对本站既有能力逐项给出判定，能力清单 MUST 至少包含：中文优先排版、默认语言无前缀的双语路由、缺失译文回退与规范链接、目录驱动的书籍章节与分组、全站静态搜索、内容图片灯箱、暗色模式、动态社交分享图。
- **FR-013**: 每项能力判定 MUST 标注为"可直接沿用 / 需改造 / 需重建 / 与主题冲突"之一，并 MUST 给出判定依据。
- **FR-014**: 报告 MUST 区分"主题原生能力"与"需自行实现的能力"，MUST NOT 把社区插件或自建方案记为主题自带。
- **FR-015**: 报告 MUST 完整呈现候选池，不得因风格取向预先淘汰；候选 MUST 按视觉风格分档归组（例如极简排版、Material Design 3、动漫/插画、终端/复古、杂志编排等），分档口径 MUST 可复核。
- **FR-016**: 报告 MAY 给出顾问性推荐与排序，但 MUST 明确最终选择权归维护者，并 MUST NOT 用"推荐"字样替代完整候选池的呈现。
- **FR-017**: 对被推荐的每个主题，报告 MUST 给出移植路线，包含阶段划分、每阶段产出、验证方式与回退点。
- **FR-018**: 移植估算 MUST 区分可直接复用的静态资源（样式、字体、图像）与必须重写的模板逻辑，并 MUST 标注各阶段的相对工作量。
- **FR-019**: 每项关键结论 MUST 附可核实来源（官方文档、仓库记录或演示站点），MUST NOT 出现无来源的星标数、性能数字或生态规模断言。
- **FR-020**: 报告 MUST 标注调研截止日期与数据时效性限制，并 MUST 指出哪些结论在该日期后可能失效。
- **FR-021**: 报告 MUST 以中文撰写，术语首次出现时 MUST 附英文原名，便于后续查阅官方文档。
- **FR-022**: 报告 MUST 明确说明最终站点仍以纯静态产物托管在 GitHub Pages、无服务端运行时；若某主题需要服务端能力才能保留某项视觉效果，MUST 写出该取舍。
- **FR-023**: 报告 MUST 明确说明移植完成后的目标是什么、不做什么：只替换外观与版式，还是同时替换内容模型与路由。
- **FR-024**: 报告 MUST 提供候选池的可核算总数：检索命中数、纳入数、未纳入数，并说明未纳入的可归因原因分布。
- **FR-025**: 本次交付物 MUST 仅限调研报告本身；MUST NOT 创建、修改或删除 `src/`、`package.json`、`astro.config.ts`、`astro-paper.config.ts`、`.github/workflows/` 等应用与部署相关文件，MUST NOT 安装或移除依赖。
- **FR-026**: 报告中的移植路线 MUST 作为后续工作的建议记录，MUST NOT 在本次执行，且 MUST 明确标注"待维护者选定主题后再启动"。

### Key Entities *(include if data involved)*

- **候选主题记录**：一个被评估的博客主题，包含仓库标识、星标数、创建与更新时间、许可证、原始生态与技术栈、演示地址、演示可达状态、视觉评估结论、纳入或未纳入状态。
- **未纳入记录**：一次检索命中但未进入深度核验的主题，包含仓库标识、命中的查询式与未纳入的具体原因，用于核算检索覆盖率。
- **视觉评估维度**：一组可复核的外观判断标准，包含维度名称、判断口径与评分。
- **本站能力项**：当前站点已交付的用户可见能力，包含能力名称、现状实现方式（仅作为对照基线）、在候选主题中的判定结果。
- **移植阶段**：移植过程中的一个可独立验收单元，包含阶段名称、产出物、验证方式与回退点。
- **证据来源**：支撑某条结论的仓库记录、官方文档或演示站点，包含来源类型、链接与访问日期。
- **检索查询式**：一次 GitHub 高级搜索的完整条件组合，包含限定符、参数值与命中数量。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 维护者可在 20 分钟内从候选池中圈定待移植主题，无需额外搜索。
- **SC-002**: 候选主题不少于 12 个，且每个候选都有可访问演示链接，缺项率为 0；演示不可达者 MUST 计入并单独标注，不得为凑足数量而省略。
- **SC-003**: 检索覆盖率可核算：报告给出检索命中数、纳入数与未纳入数，三者相加闭合，且未纳入项均有归因记录。
- **SC-004**: 候选主题的生态覆盖不少于 3 类（Astro、Hugo、Next.js 各至少 1 个），且至少 25% 的候选创建或进入快速增长期在调研截止日前 12 个月内。
- **SC-005**: 报告为本站能力清单的每一项都给出候选主题判定，覆盖率 100%，且每项判定均带依据。
- **SC-006**: 抽查 10 条关键结论时来源缺失数为 0，星标数与更新时间均可通过仓库页面复核。
- **SC-007**: 候选池按视觉风格分档呈现，档数不少于 4，且每档至少含 1 个候选。
- **SC-008**: 若报告给出顾问性推荐，每个被推荐主题都具备不少于 3 个可独立验收的移植阶段，且每阶段有明确完成判据与回退方式。
- **SC-009**: 报告明确列出当前 AstroPaper 主题在视觉上的 3 项以内主要短板，或明确说明无需更换主题。
- **SC-010**: 报告中的检索查询式可直接复制执行，且能在 GitHub 上复现出包含主要候选的结果集。
- **SC-011**: 交付完成后 `git status` 中的变更仅限 `specs/` 与 `.specify/` 下的文档，应用代码、依赖清单与工作流文件零改动。
- **SC-012**: 交付物中不存在任何截图、缩略图或视觉拼版文件，视觉判断均可通过演示链接与仓库源码复核。

## Assumptions

- 目标框架已确定为 Astro，调研不再涉及框架替换；约束是"主题可跨生态取材，但落地实现必须为 Astro"。
- 视觉风格不做预设限制：极简排版、Material Design 3、动漫/插画、终端/复古、杂志编排等均可进入候选，报告按风格分档呈现，由维护者最终评审决定。
- 候选池的完整性优先于结论的收敛性：宁可呈现更多候选让维护者筛选，也不因"不符合本风格"提前淘汰。
- 候选池不设数量上限，但"全部纳入"以显式纳入条件为界（博客/写作用途、近 12 个月有提交、有可访问演示链接）；不满足条件者记录为未纳入，不进入深度核验。
- 深度核验包含演示链接核验、视觉维度判定、能力判定与移植代价；不包含截图抓取。若候选池数量达到数百量级，报告 MUST 以可检索的表格或分档清单组织，避免可读性崩塌。
- 维护者为中文技术博客与书籍站点的唯一决策者，读者规模与访问峰值不构成选型约束。
- 站点继续以纯静态产物托管在 GitHub Pages，无服务端运行时。
- 现有内容以 Markdown/MDX 文件存放，移植成本主要由目录约定与前置数据决定，而非正文格式。
- 调研结论以 2026-11-17 为信息截止日期；此后的版本与热门变化不在本次范围。
