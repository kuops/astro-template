# Phase 0 研究：博客主题调研与 Astro 适配

**调研截止日期**：2026-11-17
**研究目的**：解决 `plan.md` 技术上下文中所有未决问题，使得"候选池无上限、每候选深度核验、
只出报告不改代码"这三条已澄清约束在 GitHub 真实 API 边界内可执行。

## 结论摘要

| 编号 | 问题 | 决定 |

## R1：GitHub 搜索的结果集边界

**决定**：采用分桶查询（bucket partitioning），不使用单一查询 + 分页。

**依据（实测）**：

- REST v3 `GET /search/repositories` 在第 11 页（`per_page=100`）返回
  `422 Only the first 1000 search results are available`。
- GraphQL `search(type: REPOSITORY)` 遍历 `topic:hugo-theme` 时，第 10 页
  `pageInfo.hasNextPage` 变为 `false`，而同一查询的 `repositoryCount` 为 **1707**。
  即 GraphQL 也在 1000 条处静默截断——这一点比 REST 更危险，因为 REST 会报错，GraphQL
  只是"看起来取完了"。

**理由**：若直接分页，`topic:hugo-theme`（1707）、`topic:blog-theme`（1019）都会丢失 700+
与 19+ 条，且 GraphQL 路径下丢失是静默的，报告会误称"已全部覆盖"。

**备选方案与否决原因**：

- 单一查询 + 深分页：被 1000 条上限否决。
- GraphQL 单次大 `first` 值：`first` 上限 100，且仍受 1000 条总量约束，否决。
- 按 `created:` 或 `pushed:` 时间分桶替代星标分桶：可作补充维度，但时间分布不均（新主题集中），
  单独使用会产生同样超限的桶，故以星标为首要分桶键。

## R2：分桶策略的正确性验证

**决定**：以星标区间作为主分桶键，桶顺序如下：
`0..1`、`2..2`、`3..5`、`6..10`、`11..50`、`51..100`、`101..500`、`501..1000`、`>=1001`。

**依据（实测）**：对 `topic:hugo-theme` 逐桶统计并求和无条件值：

```text
stars:0..2    => 1007   <-- 单桶仍超 1000，需再切
stars:3..5    => 124
stars:6..10   => 101
stars:11..50  => 190
stars:51..100 => 91
stars:101..500=> 141
stars:501..1000=>27
stars:>=1001  => 26
sum = 1707 == unfiltered 1707
```

将 `0..2` 细分为 `0..1`（826，加 `archived:false` 后）与 `2..2`（112）后，每桶均低于 1000。

**理由**：分桶和与全量完全相等，证明该切法无重叠、无遗漏（星标区间互斥且完备）。

**关键细节**：分桶后必须校验 `Σ(桶计数) == 无条件计数`，不等即说明有桶超限被截断，必须继续细分。
此校验本身即为覆盖率的机器证明，应写入报告。

## R3：仅用 `topic:` 检索会漏掉高星标主题

**决定**：采用四路召回并行，结果取并集并去重。

1. **topic 路径**：`topic:astro-theme`、`topic:astro-blog`、`topic:astro-template`、
   `topic:hugo-theme`、`topic:blog-theme`、`topic:nextjs-blog` 等。
2. **keyword 路径**：`astro blog theme in:name`、`astro blog theme in:description`、
   `hugo theme blog in:name`、`nextjs blog theme in:name`。
3. **seed 路径**：从 `one-aalam/awesome-astro`、`theNewDynamic/awesome-hugo` 等
   聚合清单的 README 中抽取仓库链接（实测 `awesome-astro` 单文件可抽出 61 个仓库引用）。
4. **recent 路径（新增，见 R9）**：`created:>2025-11-17` 的时间窗口召回，
   用于落实 spec FR-004 的"近期新增高增长"要求。

**依据（实测）**：

- `LyraVoid/Shirone`：452 星，**topics 为空数组**，纯 topic 检索无法命中。
- `incluud/accessible-astro-starter`：1194 星，topic 为 `blog, template, theme...`
  但**不含** `astro-theme`，仅在 `stars:>300` 的通用关键词查询中浮现。
- `LyraVoid/Mizuki`：1888 星，已 `archived: true`，topic 亦为空。

**理由**：这是"不要漏掉"要求下最实质的风险。三种召回路径互补：topic 精度高但覆盖不全，
关键词覆盖广但含噪声，种子清单能捞到连关键词都描述不清的项目。

**备选方案与否决原因**：`in:readme`（实测 36065 条）噪声过大，否决；仅用 topic 路径会漏掉
上例三个高星标项目，否决。

## R4：噪声控制与纳入条件

**决定**：检索命中不等于纳入。纳入必须同时满足：

1. 用途匹配：仓库自述/README/topic 指向博客、写作、内容站点或文档站点主题。
2. 活跃度：`pushed:>2025-11-17`（近 12 个月），且 `archived:false`。
3. 演示可核验：存在 `homepageUrl` 或 README 中可提取的演示链接。

不满足者在报告中记为"已检索未纳入"，附具体原因。

**依据（实测）**：`archived:false` 使 `topic:hugo-theme` 从 1707 降至 1557；叠加
`pushed:>2025-11-17` 后降至 696。即使不加星标门槛，纳入量已落在可人工核验的范围内。

**理由**：spec 的 FR-005 要求"不设数量上限"，FR-006 要求"以显式纳入条件为界"。
本决定把"上限"从数量转移到条件，使"全部纳入"可执行且可审计。

## R5：演示链接可达性

**决定**：以 `homepageUrl` 为首选演示地址，缺失时从 README 提取第一个非仓库自身的 http 链接，
仍缺失则标注"无演示链接"。抓取时记录 HTTP 状态码与最终 URL，超时 12 秒。

**依据（实测）**：

- `topic:astro-theme stars:>20` 的 65 个仓库中，64 个有 `homepageUrl`，1 个为空。
- 对前 30 个候选实测可达性：**29 个返回 200**，1 个返回 402。
  402 来自 `astrowind.vercel.app`，是 Vercel 的平台侧限制，不是站点下线。

**理由**：证明 spec 的 SC-002（每候选都有可访问演示链接，缺项率 0）在实际上可达 97%+，
剩余部分可归因为平台限制并单独标注，不需要降低标准。

**重要细节**：`homepageUrl` 可能是产品购买页（如 `themefisher.com/products/...`）而非主题演示，
必须人工区分"演示站"与"商品页"，后者记为"演示不可达（仅商品页）"。

## R6：速率限制与执行策略

**决定**：单线程串行执行，请求间隔 ≥ 2.5 秒，所有中间结果落盘为 NDJSON，
任何中断均可断点续跑。

**依据（实测）**：

- `search` 资源限流为 **30 次/分钟**，实测连续查询会触发
  `403 API rate limit exceeded`。
- `core` 资源为 5000 次/小时，`repos/{owner}/{repo}` 单仓库详情走 core，不受搜索限流影响。
- GraphQL 走 `graphql` 资源（5000 点/小时），单请求可批量取回星标、许可证、语言、
  最新 release、topics、homepage，等效替代 6~8 次 REST 调用。

**理由**：分桶会使请求数从"每个 topic 1 次"放大到"每个 topic 9~12 次"。以 6 个 topic、
3 条召回路径估算，**仅计数阶段就需约 150 次搜索请求**，约需 5 分钟；再叠加候选详情，
总量在 250 次量级。若不限速会被限流打断，若不落盘则重跑成本极高。

**执行顺序**（必须遵守，先轻后重）：

1. 计数阶段：只取 `total_count`，每桶 1 次请求，用于验证分桶闭合。
2. 列表阶段：分页取仓库节点（GraphQL，`first:100`），每桶 1~10 次请求。
3. 详情阶段：对已纳入候选取 `homepageUrl`、`licenseInfo`、`latestRelease`（可与阶段 2 合并）。
4. 可达性阶段：`curl` 探测演示站，**不消耗 GitHub 配额**，可并发。

## R7：报告交付形态

**决定**：

- 主交付物：`specs/001-blog-framework-research/research-report.md`（中文 Markdown）。
- 机器可读附表：`specs/001-blog-framework-research/candidates.csv`，字段与
  `data-model.md` 的候选主题记录一致，供排序与筛选。
- 检索凭证：`specs/001-blog-framework-research/queries.md`，记录每条实际执行的查询式与命中数。
- 不生成任何图像文件（遵循 spec FR-009 与 SC-012）。

**理由**：CSV 让"无上限候选池"可被排序、过滤、统计，弥补 Markdown 表格在数百行时的可读性
崩塌问题；查询凭证让 SC-010（查询可复制复现）可被直接检验。

**备选方案与否决原因**：单一巨型 Markdown（放弃）——数百行表格无法排序；生成 HTML 站点
（放弃）——要求引入构建步骤，违反"只出报告不改代码"的边界；JSON（放弃）——人类不可直读，
与"由维护者评审"的用途不符。

## R8：不截图前提下的视觉评估口径

**决定**：视觉维度评分必须基于以下三类可核实来源之一，并在报告中逐条标注来源类型：

1. **演示站可观察特征**：填写演示 URL 与访问日期，描述可被他人打开同一 URL 复核的特征
   （如"首页标题字号明显大于正文字号，形成 3 级阶梯"）。
2. **主题源码设计令牌**：引用仓库中具体文件的字体栈、间距刻度、配色变量，
   给出路径与行号级定位。
3. **仓库文档声明**：README 中明确写出的设计特征（如"Material Design 3"），标注为
   "据仓库自述，未独立验证"。

**理由**：spec FR-011 明确禁止声称视觉结论来自未生成的截图。此口径把"好看"拆成可复核的
可观察特征，使维护者能在不信任报告主观判断的前提下自行验证。

**备选方案与否决原因**：直接给主观评分（否决）——不可复核，违反 FR-011；
只给演示链接不做任何判断（否决）——退化为链接列表，无法支撑 US1 的"统一维度比较"。

## R9：近期新增高增长的召回缺口

**决定**：新增第四路召回 `recent`，以 `created:>2025-11-17` 为时间窗口，
叠加 `archived:false pushed:>2025-11-17`，并按星标分桶。

**依据（实测）**：

`topic:astro-theme` 在近 12 个月新建的项目分布：

```text
created:>2026-09-01            => 101
created:2026-06-01..2026-09-01 =>  51
created:2026-01-01..2026-06-01 =>  37
created:2025-06-01..2026-01-01 =>  23
```

在此窗口内、星标 >20 的主题包括：`0xdres/astro-devosfera`（189 星，2026-02-16 创建）、
`cxro/astro-whono`（176 星，2026-01-16）、`devgelo-labs/astro-starter-pro`（61 星）、
`webrating/starfolio`（57 星）、`erlandv/case`（53 星）、`anjay-goel/astro-sienna`（51 星）、
`xocothemes/quietpages`（38 星）等。

**问题**：前三路召回（topic / keyword / seed）均按**累计星标**排序或按 topic 匹配，
这些新项目星标数远低于既有头部主题，在 1000 条上限下极易被挤出可见范围。
若不单独召回，spec FR-004 的"不得漏掉新近走红项目"与 SC-004 的"至少 25% 候选为近 12 个月
新增"都无法成立。

**理由**：`created:` 是独立于星标的维度。按星标分桶时，新项目全部落在低星标桶，
而低星标桶（`0..1`）在 `hugo-theme` 下就有 333 条，新项目在其中毫无区分度。
只有用 `created:` 显式切出时间窗，才能保证这批候选被看见。

**备选方案与否决原因**：

- 仅靠星标排序取前 N：否决——必然偏向老牌项目，与 FR-004 冲突。
- 用 `created:` 替代星标分桶：否决——新项目集中会导致时间桶同样超限（`>2026-09-01` 已有 101 条，
  若不加星标约束在 `hugo-theme` 下会更大），须两维并用。
- 用"星标增速"排序：否决——GitHub 搜索不支持增速维度，需自建历史快照，超出本次范围。

**下游约束**：`tasks.md` 必须包含 `recent` 路径召回任务，且报告中必须给出
"候选池中创建于近 12 个月的比例"，用于验证 SC-004。

## 未决事项

无。所有 `NEEDS CLARIFICATION` 均已在上述 R1–R9 中收敛。

## 对下游的约束提醒

- `tasks.md` 必须把 R1 的 1000 条上限当作硬约束处理，不得写成"遍历全部分页"。
- 任何声称"覆盖全部结果"的产出，必须以 R2 的分桶闭合校验为前提，否则视为未验证。
- R3 的四路召回缺一不可，尤其 `seed` 与 `recent` 两路：
  缺 `seed` 会漏掉 `LyraVoid/Shirone` 类零 topic 项目，
  缺 `recent` 会使 SC-004 的"25% 新近"无法达成。
- FR-008 要求的"最近发版时间"必须来自 `latestRelease`，无发行版者记 null，
  不得用 `pushed_at` 冒充。
